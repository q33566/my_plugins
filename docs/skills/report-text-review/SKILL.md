# report-text-review

把一份報告的**文字**審乾淨：刪掉不該存在的字，剩下的每個字都精準。
只審文字，不重算數字、不改圖表資料。

## 為什麼用 subagent

審查員必須是**沒參與寫作的人**。主 session 看自己的稿，會替每個句子找理由留下。
所以：審查交給 fresh-context subagent，**主 session 只負責判斷與套用**。

## 問題等級（所有步驟共用）

- **A 必修**：讀者會看不懂、讀錯或被誤導。例如：詞沒定義就用、劇透、數字沒交代算法、圖看不懂、前後矛盾、沒有來源的主張。
- **B 該修**：讀得懂，但費力或不精準。例如：贅字、重複、空泛詞、口語用詞。主 session 判斷後修。
- **C 可不修**：風格偏好，修不修都不影響理解。

**「清零」指 A 全部修完**，才能發布。B 可以保留，但要在回報裡說明為什麼留。審查**沒有輪數上限**：A 沒清零就繼續改、繼續審，修到完為止（user 明定）。

**第 2 輪起附「不改清單」**：派工時附上前幾輪判定不改的項目與理由。審查員可以重提，但必須給出和清單上不同的新理由；只重複舊理由的不算數。主 session 每輪都把新判定的「不改」項目加進清單。

## 輕量版與完整版

主 session 依文件判斷用哪一級，並在回報裡說明：

| | 適用 | 走哪些步驟 |
|---|---|---|
| **輕量版** | 約一頁內、沒有圖：變更摘要、日報、說明文字 | 0、3、6（三位合併成一位，三個判準都要審）、7、8＋9（合併成一位）、10 |
| **完整版** | 有圖或超過一頁：實驗報告、設計文件 | 全部步驟 |

兩級都不變：冷讀一定要做、A 清零才能發布、沒有輪數上限。

## 流程（順序固定：先讀得懂，再刪，再磨字）

### 準備

#### 0. 寫下讀者與目的
兩行，派工時附給第二、三關的每位審查員：
- **讀者**：誰在讀（例：要決定能不能合併的審查人）。
- **讀完要做什麼**：（例：判斷能不能合併）。

不確定就問 user，不要自己猜。這兩行只用來判斷「什麼該留、什麼可刪」；冷讀（步驟 3）不用它，見該步驟。

**同時先問 user：要不要有大綱／overview。** 在開審之前就確認，不要審完才補：
- 要不要放、放在哪（文件最前面，或標題下面）；
- 形式：一段摘要、條列重點，還是章節大綱；
- 已經有的話，它是不是只講到正文真的有的東西、順序是否和正文一致。

user 說要、文件卻沒有，就是 A 級；user 說不要，就把「不放大綱」列進派工時的「使用者指定的設計決定」，
審查員建議加大綱一律不採用。

**依報告格式**（步驟 1、2 共用）：

| 報告格式 | 步驟 1（純文字稿） | 步驟 2（圖） |
|---|---|---|
| HTML＋SVG | 照下面的做法 | 照下面的做法（正方形畫布＋轉 PNG） |
| Markdown／純文字 | 原檔直接用 | 沒有圖：步驟 2、5 跳過 |
| Google Doc | 先匯出成文字 | 有圖就下載成 PNG |
| 圖是 PNG／截圖 | — | 直接用 PNG；圖內文字由主 session 看圖抄出，寫成 `[圖內文字…]` |

#### 1. 準備純文字稿
把報告轉成純文字檔（HTML 去掉 style / svg，保留標題階層、段落、表格列、圖說；**圖不可用 `[圖形]` 佔位**：把每張 SVG 裡的**所有文字**（標題、軸標題、刻度、圖例、直接標在圖上的標籤與註記、色塊上的數字）依畫面由上到下、由左到右抽出，原地寫成 `[圖內文字｜圖例：…｜軸：…｜標註：…｜色塊：…]`，接在該圖圖說之前），存到 scratchpad，例如 `report_text.md`。圖內文字是讀者必讀的字，和正文同等對待，不能省略。
審查員讀這個檔，**不要讓它讀原始格式（HTML 等）或產生報告的程式**。

#### 2. 準備「圖」給審查員看（每次必做）
審查員只讀文字稿會**看不到圖裡畫了什麼**，因此抓不到「圖放錯位置」「圖含還沒介紹的東西」。必須：
1. 把每張圖輸出成 PNG，放在固定資料夾。**必須把每張 SVG 先包進「正方形畫布」（viewBox 取長邊、背景白色）再轉成 PNG**（Mac 用 `qlmanage -t -s 2200`；其他系統用任何能把 SVG 轉成 PNG 的工具，一樣先包成正方形畫布），否則寬圖的右側會被裁掉，審查員會把渲染問題誤報成圖的問題（實際發生過）。
2. 產生**圖清單**（依出現順序）：`PNG 路徑 ｜ 位於哪一節 ｜ 圖內容（標題、畫了哪些組別／系列／標註）`。
3. 派審查員時，**明確要求它用 Read 打開每一張 PNG 逐張檢查**，並附圖清單。純文字稿裡的 `[圖內文字…]` 是圖上文字的抽出版，供冷讀與各審查員逐字審；PNG 是用來看版面與圖形本身（配色、位置、有沒有畫出文字說的東西）。
4. 主 session 自己也要開每張圖看一次（版面、重疊、被截斷、軸與單位）。

### 第一關：讀不讀得懂

#### 3. 第一性原理冷讀（每次必做，第一道關）
**目的**：作者看不到自己稿子的缺口，因為作者的腦袋會自動補上缺的定義、缺的前提、缺的鋪陳。冷讀就是用一個什麼都不知道的讀者，從第一個字讀到最後一個字，逐字記下「它讀到這裡時，知道什麼、不知道什麼」。

派一位 fresh-context 的**冷讀員**（唯讀；不給背景、不給資料、不給我們的對話，也不給步驟 0 的讀者設定）。冷讀員一律扮演**完全不懂的人**：作者猜不準讀者實際懂什麼，寧可多抓缺口，再由主 session 判斷哪些不用補。它只拿到純文字稿（**含圖內文字**，見步驟 1），並被要求維護一份**「已知清單」**，邊讀邊填。**圖內每一個字都是讀者讀到的字**：圖例、軸標題、刻度單位、圖上標註、色塊標籤，都要照出現順序（圖說之前先讀圖內文字）逐字走下面 1–5 項，**不得因為「那是圖」而略過**；另外加一項：圖例或標註的每個說法，讀者能否只靠圖本身加圖說就懂它指哪一塊、和哪個色塊／系列對應？不能→記為「**圖內文字看不懂**」。（例：圖例寫「最後一輪與輪外時間」，文中從未說明這兩者為何同色）。

1. **每遇到一個詞／縮寫／代號／單位／比值**：問「到這一行為止，文中定義過它嗎？」沒有→記為「**未定義就使用**」，標出第一次出現的原句。（例：用了「基線」「對」「乾淨配對」「順序效應」卻從未定義，或定義在後面、附錄。）
2. **每個結論性句子、每張圖、每個表**：問「它依賴的前提，前面論證過了嗎？」沒有→記為「**順序錯誤／劇透**」。（例：還在找瓶頸的章節，圖已畫出「要換的地方」。）
3. **每個數字**：問「讀者能否看出它是什麼的平均／總和、幾個樣本、原始或調整後、和誰比、單位與分母？」不能→記為「**數字無口徑**」。並排的兩個數字比較基礎不同也要記。
4. **每個因果或事實主張**：問「文中有給證據或來源嗎？還是只是聽起來合理？」→記為「**無來源主張**」。
5. **每個重要的詞，全文是否只用一個名稱**（圖例、軸標題與正文用同一個名稱嗎）？同一概念兩個名稱、或一個名稱兩個意思（「組」既指一對配對、又指實驗組別）→記為「**術語漂移**」。
6b. **每個專有名詞的語體**：是否口語、俚語、比喻（例：「被丟掉的輪」「救回」「炸掉」「跑偏」）？論文與技術報告的術語要用中性、可定義的字（例：「重跑前的失敗輪」）。口語名詞即使文中定義過也要記為「**口語用詞**」，建議換成中性詞。（user 明確糾正過：「被丟掉」太口語。）
6. 最後輸出：「已知清單」的最終版（讀者讀完到底學到了哪些詞與數字）＋上面五類問題的清單（原句引文｜問題類型｜讀者卡在哪）＋「**讀完之後，讀者能不能用一句話複述這份報告的結論與依據**」。

**主 session 自己也要做同一件事**（不能全外包）：每次改完一批，從頭到尾**真的重讀全文一遍**，邊讀邊自問「第一次看到的人，讀到這裡知道什麼」。局部補丁會製造新的順序問題與新的不一致，只看被改的那一段不夠。

#### 4. 順序性（審查員做，主 session 自己也做）
**順序性＝讀者讀到某一處時，只應該被要求理解「前面已經介紹過」的東西。** 審查員要從頭到尾、依出現順序檢查**文字、表、圖三種內容**：
- **圖與表**：每張圖／表畫出的每個**實體與系列**（例如「Jev 組」「Jev 等待」），在它所在的那一節之前是否已被介紹？若一張圖在「找瓶頸（只有基線）」那節卻畫了 Jev 組，就是**劇透**，應該改成只畫基線的版本，把含 Jev 的對比圖搬到「換成 Jev 之後／結果」的章節。
- **一張圖兩個位置**：同一張圖可能需要兩個版本（基線版放前面、對比版放結果）；不要為了省事共用一張。
- **標註與圖說**：圖說或圖內標註（例如「想換掉：○○」）預告的解法，是否已在論證之後才出現。
- **名詞與數字**：與步驟 3 相同，但要同時檢查圖例、軸標籤、表欄名。
- 輸出：`位置（章節＋圖/表/句）｜問題｜建議（搬到哪一節／拆成兩版／刪掉標註）`。
- 搬移圖表後，**重新編號並更新所有引用**，再重做一次本審查。

**主 session 自己也要做**（不能只靠審查員；第二關的刪字審查員只看句子，不看「讀者讀到這裡時知道什麼」）。每次重排或刪完後，**由前往後逐段檢查**：
- 每個**術語／縮寫／名詞**是否在第一次使用之前就已定義？（例：「對」「乾淨配對」要在用它的數字之前說明）
- 每張**圖／表**是否只呈現「到那一節為止已論證過」的內容？（例：還在找瓶頸的章節，圖不能已經標出「要換的地方」；那是劇透）
- 報告的**論證順序**是否與 user 指定的流程一致？（例：先瓶頸 → 哪裡可換 → 這次換了哪裡 → 怎麼換 → 數據）
- 結論性字句（「本研究要換的是…」「所以…」）是否出現在證據之前？
做法：把全文照順序掃一遍，每遇到一個「前面沒出現過的概念」就標記，決定是前移定義、刪掉、或延後出現。

#### 5. 圖必須能獨立讀（每次必做）
**規則（user 明定）：每張圖必須脫離正文與圖說也能讀懂。** 圖內要有：標題、軸標題與單位、每個圖例／色塊的完整說法（含該詞的白話定義）、樣本數與分母、圖上標註的實際值。不能指望讀者回頭去讀「用詞」或正文。
做法：派一位**只拿 PNG、不給任何文字稿與圖說**的空白審查員，對每張圖回答：(1) 圖在講什麼、結論是什麼；(2) 每個色塊／圖例／標註／軸／數字是什麼意思，逐項標 UNDERSTOOD／NOT UNDERSTOOD 並說缺什麼；(3) 兩個讀者會不會讀出不同意思。任何 NOT UNDERSTOOD 或可能誤讀都是 A 級，改圖本身（不是改圖說）後重審。

**名詞定義位置（論文慣例，user 要求照做）**：不要在摘要／重點之前放「用詞」總表。論文與技術報告的術語在**引言或背景第一次用到時就地定義**。需要的定義寫進引言段落或第一次出現處的括號；圖內的詞則由圖本身帶定義（上一段）。

### 第二關：刪

#### 6. 平行派三位審查員（一則訊息同時送出）
每位都是唯讀（不修改任何檔案），輸出格式相同：
`原文引文（12–40 字、必須能在檔案裡 grep 到）｜建議｜一句理由`，按可省字數排序，上限 40–50 筆，不稱讚、不總結。

| 審查員 | 判準 | 要點 |
|---|---|---|
| A 贅字 | 刪掉後句意與資訊**完全不變**的字、詞、整句 | 重述上一句、堆疊的「大約／基本上」、「也就是說」後只換句話說、圖說重述圖名；只列零資訊損失的。段落開頭預告內容的導航句（「接下來看三個原因」）是替讀者帶路，不算贅字。**否定式鋪陳句**（「不是用猜的，工具會讀取…」「不會卡住，它會跳過檢查直接執行」）：如果緊接著的那個子句本身已經證明／蘊含這個否定（讀取真實紀錄＝不是用猜的；跳過檢查繼續執行＝不會卡住），前面那句否定鋪陳就是贅字，刪掉、直接從證明那半句開始 |
| B 資訊重複 | 刪掉某處後，**報告其他地方仍完整保有同一資訊**（同事實／同數字／同解釋） | 每筆要指出「資訊另外保留在哪一處」；兩處不完全等價就不列；優先刪較不重要或較冗長的那處；摘要是刻意的濃縮，只在逐字重複時才動 |
| C 必要度 | 扮演步驟 0 的**讀者**（沒寫時預設：沒參與專案、要靠這份報告做決定的主管）：少了這段，我還能完成「讀完要做的事」嗎？會看不懂、或無法相信結論嗎？都不會→刪 | 「結論依賴的證據」「讓數字可信的方法說明」「限制」不可建議刪；**另外單列「看不懂的地方」**（缺定義、前後矛盾、數字對不上） |

派工 prompt 範本（把 `<路徑>` 換成純文字稿）：

```
你是一位嚴格的 <中文技術文件編輯／技術報告編輯／技術主管>。請只讀（不要修改任何檔案）這份報告的純文字稿：<路徑>
（`[圖內文字…]` 是 SVG 圖上文字的抽出版，要和正文一樣逐字審；數字是從資料算出來的，不要質疑數字本身。）
讀者與目的：<步驟 0 的兩行>
任務：<該審查員的判準>
規則：
1. 每一筆給：原文引文（一定要是檔案裡可 grep 到的連續原文，12–40 字）｜建議｜一句理由。
2. <該審查員的要點>
3. 按可省字數由大到小排序，最多 N 筆。不要稱讚、不要總結、不要列沒問題的部分。
輸出純文字清單。
```

#### 7. 主 session 判斷並套用（不是照單全收）
**先合併成一張表**（每輪一張，存在 scratchpad）：

```
編號｜原文引文｜誰提的（A/B/C…）｜等級｜建議｜判定（改／不改＋理由）
```

- 引文指到同一段原文的，併成同一列，「誰提的」列出所有提的人。
- 判定為「不改」的列，就是下一輪的不改清單；收尾回報「沒採用哪些建議與原因」也從這張表整理。

審查員的建議是**候選**，逐項判斷：

- **user 明確要求過的內容不刪**（例如 user 說「要講清楚」的解釋、要的範例、要的圖）。審查員 C 常建議刪這類內容（統計教學、單一範例、整張圖）；這種情況改成**縮短**而不是刪除，並在回報裡說明。
- 兩位審查員指向同一處且理由成立 → 套用。只有一位提、且你判斷刪了會損失資訊 → 不套用。
- **兩處重複，保留哪一處**：保留讀者最需要在那個位置理解的那處；數字多半留在表，結論留在正文，摘要只放最濃縮的版本。
- 刪除後檢查**前後文是否還接得上**（代名詞、「如上所述」、章節與圖表編號、指向被刪內容的引用）；圖／表被刪後要重編號並更新所有引用。
- 套用方式：改產生報告的程式（或原始檔），重新產生，再重新產出純文字稿；不要手改產物。
- 每套用一批，抽查 5 處確認改的是對的位置、沒有把數字或變數改壞（f-string 的大括號、`None`、`nan`）。

**處理「看不懂的地方」**：
審查員 C 的「看不懂的地方」是**最有價值的輸出**。逐條處理：缺定義→補一句定義；數字不一致→全報告統一口徑（同一個量只用一種算法，另一種算法加註）；樣本數混亂→補一張「樣本一覽」。這些是補，不是刪。

### 第三關：磨字

#### 8. 派第四位：精準度與空泛口語（只對剩下的文字）
第二關結束後，剩下的都是必要資訊。再派一位審查員，判準：

- **空泛口語**：「大概、差不多、有一些、比較好、很明顯、看起來、不太、蠻」→ 能不能換成數字、範圍、或明確條件？
- **含糊指涉**：「這個、那個、它、其中、上述」所指不唯一。
- **主觀形容**：「明顯、顯著、很大、很快」沒有量化依據（「顯著」只在有檢定時才能用）。
- **口語連接**：「所以說、其實、基本上」。
- **術語漂移**：同一概念用兩個名稱（例如「模型呼叫」「LLM 呼叫」「決策次數」）。
- **過度肯定或過度保留**：證據只支持「看不出差別」卻寫「沒有差別」；已確定的卻寫「可能」。

- **數字沒有口徑**（最容易漏，必須單獨列為一個檢查項，且**這一項要求審查員質疑「數字怎麼被描述」，不質疑數字本身**）：每個出現的數字，讀者能否從那句話本身看出
  - 它是**什麼的平均／中位數／總和**（哪一群樣本、幾個）？
  - 是**原始值還是調整後的值**（例如有沒有扣掉順序效應、有沒有排除重試）？
  - **兩個數字並排時比較基礎是否相同**（例如「313 秒對 307 秒」是原始平均，而同一段的「0.97」是調整後比值；兩者並排卻沒說明，讀者會以為是同一件事）。
  - **單位與分母**（秒／次／%、占誰的幾分之幾）。
  - 同一個量在報告不同處是否用了不同算法（−20% 與 −29%）。
  替換句要把口徑補進句子，例如「90 對乾淨配對的原始平均：基線 313 秒、Jev 307 秒（未扣除順序效應）」。

輸出格式：`原句｜問題類型｜替換句（必須保持原意、不得新增事實）`，最多 40 筆。

主 session 套用時，**替換句不得引入原文沒有的事實**；若替換需要新數字，從資料取，不要憑印象。

#### 9. 派第五位：中文文字（只對剩下的文字，可與步驟 8 同一則訊息平行派出）
判準是「讀起來順不順」，不碰內容與數字：

- **歐化句**：「被」字句過多（「錯誤被系統發現」→「系統發現錯誤」）；虛動詞（「進行驗證」→「驗證」、「做出決定」→「決定」）；「的」連用；過長的修飾語。
- **段落**：每段第一句是否先講這段的結論；段與段之間是否接得上；標題能不能就是結論（「r79 已上線」優於「發布狀態」）。
- **一致性**：繁簡混用（只查作者寫的正文，模板規定的固定標題不算）；中英夾雜（產品名與專有名詞照用英文，有通用中文說法的詞改中文，例：「review」→「審查」）；全形、半形標點混用。
- **節奏**：連續多句長度相同，或一句長到要回頭重讀。

輸出格式同步驟 8：`原句｜問題類型｜替換句（必須保持原意、不得新增事實）`，最多 40 筆。這些一般是 B 級，主 session 判斷後套用。

### 收尾

#### 10. 再冷讀、發布、回報
- **再做一次步驟 3 的冷讀**（全新的冷讀員）：第二次回報沒有 A 級問題（A 清零），才算完成，之後才能發布。
- 重新產生報告、重新產純文字稿，統計字數變化（前後字數）。
- 回報：刪了什麼類別、沒採用哪些建議與原因（特別是 user 要求過的內容）、補了哪些定義、字數 前→後。
- 若報告已發佈（artifact 等），用同一個網址更新，並說明版本。

## 常見坑（來自實際審查）

- **冷讀員只拿 `[圖形]` 佔位，圖例沒人讀**：圖例「重跑的執行：最後一輪與輪外時間」這類字，作者看得懂、冷讀員從沒讀到，user 讀報告時才發現看不懂（實際發生過）。圖內文字一律抽出給冷讀員，並把「圖內文字看不懂」列為固定問題類型。

- **不要問 user「要不要再跑一輪審查」**：套用修正後，A 沒有清零就**自己再跑**，直到沒有 A 級問題才停（user 指定的設計、四捨五入這類已說明項不算 A）。把這個決定丟給 user 是失職（實際發生過）。

- **派工 prompt 必須附「使用者已指定的設計決定」清單**：審查員不知道對話裡 user 的要求，只會套用一般報告慣例（例如「結論放最前面」「刪掉細節」「圖重複」），結果建議推翻 user 明確要求的結構。每次派工都要列出並聲明「以下是使用者指定、刻意的設計，不要報告」，例如：結論放最後、哪些圖必須存在、哪些內容已被要求刪除（區間、森林圖、不同切法）、表格與用語的偏好。主session 收到與清單衝突的建議時一律不採用。

- **發佈前必須等審查通過**：不能「一邊發佈一邊跑審查」。順序：改 → 全套審查（冷讀＋順序性＋贅字／重複／必要度＋精準度，含看圖）→ 套用 → 再審 → A 清零後才發佈或更新。User 抓到過兩次我跳過或搶先發佈。
- **精簡版也要走完整流程**：從完整版刪減出精簡版，會同時產生新的順序問題（例如結論引用後面才有的圖）與數字口徑缺口，必須重審，不是刪完就好。
- **圖搬位置會連動**：圖放進另一節後，圖說裡的名詞、標註、章節引用都要跟著檢查。
- **Execute 對比圖的案例**：「基線與 Jev 並排」的時間拆解圖放在「時間花在哪」會劇透；正確做法是前面放只含基線、標出想換掉的部分的版本，結果章節才放並排版。

- **作者常用的詞最容易漏定義**（例如「基線」「乾淨配對」）：作者天天用，所以看不到它們沒被定義；摘要最容易犯，因為作者以為摘要只是濃縮。修法照步驟 5：在第一次出現的地方就地定義。
- **圖會劇透**：流程圖若在「找問題」的章節就標出「解法」，順序就錯了。每張圖只能呈現到該節為止已論證的內容。
- **「怎麼算出來」要有圖**：重要結論數字（例如 0.97）若只有文字描述，讀者無法驗證；給一張畫出所有原始樣本、並標出彙總值的圖。
- **解釋三次還沒懂 → 不是讀者的問題**：換成最白話的字面拆解（每個符號、每個數字各代表什麼），不要換一個更精簡的統計說法。
- **局部補丁會製造新問題**：每批修改後重讀全文，重新編號圖表並更新所有引用。

- **只查「空泛字詞」會漏掉「具體但口徑不明」的句子**：「整個測項 313 秒對 307 秒」每個字都精確，但沒說是原始平均、沒扣順序效應，讀者無法判斷它和「0.97」的關係。派第四位審查員時，**必須明確要求檢查數字口徑**（見步驟 8），不能只給「空泛口語」清單；也不能叫它「不要質疑數字」而不補一句「但要質疑數字被怎麼描述」。

- 同一個量出現兩種數字（例如「調整後 −29%」與「原始平均 −20%」）：審查員 C 一定會抓。統一口徑再審。
- 圖說重述圖名、軸標題、或正文已寫的結論 → 最常見的贅字來源。圖說只留「怎麼讀」。
- 摘要／結果總覽／結論三處講同一件事：保留摘要（濃縮）與結果總覽（表），結論只留**建議**。
- 名詞解釋附錄重述正文剛定義過的詞 → 刪，只留正文沒解釋的。
- 審查員會建議刪「方法說明」；判斷標準是「讀者是否需要它才能信任數字」。
- 審查員引文必須能 grep 到；找不到的建議視為無效（可能是它改寫了原文）。

- **否定式鋪陳句是贅字審查員會漏抓的一類**（實際發生過：user 自己抓到「不是用猜的，工具會直接讀取自己判斷當下實際叫出來看過的畫面紀錄」——後半句本身就證明了「不是用猜的」，前面那句純屬多餘；同一份文件裡「不會卡住，它會跳過檢查、直接用現有版本繼續執行」也是同一個模式）。這種句子讀起來很順、像是在替讀者打預防針，審查員容易放過。主 session 自己重讀時要額外問一次：「這句否定，後面的子句有沒有自己就證明了？」有→刪前面那句。

- **逐字引用真實畫面/錯誤文字，要跟全文既有敘述交叉核對，不是只核對引文本身準不準**（實際發生過：手冊原本寫「螢幕暗掉或鎖著都沒關係，工具會自動把螢幕點亮、解鎖」，這句本身沒錯；後來為了求真實，把程式碼裡「找不到手機」那段錯誤訊息整段逐字貼進疑難排解章節，裡面有一句「螢幕已解鎖」被當成前提條件列出——兩句話乍看都對程式碼負責，合在一起卻是矛盾：一處說鎖著不影響，一處把解鎖當成必要條件。冷讀員跟必要度審查員各自獨立抓到同一處）。問題不在引文不準，而在**只核對了新加的那句話本身對不對，沒有回頭核對全文裡所有講同一主題的句子合不合**。逐字引用程式碼字串（錯誤訊息、CLI 提示、UI 文字）時，套用前**先搜尋全文有沒有其他地方講過同一件事**，合不起來就要麼調解措辭（例如分清楚「偵測到之後」vs「偵測到之前」兩個不同階段），要麼兩處都重寫到彼此不衝突；不能因為引文逐字正確就跳過這一步。
